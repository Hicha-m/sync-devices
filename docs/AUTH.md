# AUTH-001: bootstrap and device pairing

Implementation: `server/sync_devices/auth.py`. This is the **API foundation**; there is no UI, WebRTC or production deployment configuration yet.

## Threat model / trade-offs

- Device bearer credentials are 256-bit random secrets generated by the server; their **SHA-256 digests** are stored in SQLite. They are returned only once to the enrolling device. Store client-side credentials in protected application storage where supported. Avoid plaintext browser localStorage for production long-lived secrets; XSS would expose them. Future PWA work must define robust storage and CSP before deployment.
- The `identity_public_key` field is metadata only and **not** cryptographically verified in AUTH-001. Do not claim asymmetric device authentication. It is reserved for signed challenges in a future version.
- An authenticated administrator issues a random, one-use invite for a specific user; expires in five minutes. The invite is a **secret**, not a short human-friendly 6-digit code; it can be transferred by QR or other trusted out-of-band mechanism.
- A session is an opaque random bearer token valid for 24 hours. Sessions are stored hashed. A device secret can obtain a new session. Revocation deletes the device secret and active sessions.
- Anyone in possession of the administrator bootstrap secret **before first initialization** can claim the instance. Set it securely as an environment variable before exposing the service; never use a checked-in secret.
- HTTPS is mandatory by default. `allow_insecure_http=True` exists only for localhost development/testing and should never be used on an exposed LAN interface.
- No rate limiting, audit log or reverse proxy configuration yet. Production deployment is **not ready** until these and credential handling safeguards are added.
- Use distinct app users for people, and distinct devices for each installation. Invite issuance and user creation are admin-only.

## Run on loopback (development only)

```bash
python -m pip install -r server/requirements-dev.txt
export SYNC_BOOTSTRAP_SECRET="$(python -c 'import secrets; print(secrets.token_urlsafe(40))')"
PYTHONPATH=server uvicorn sync_devices.main:app --host 127.0.0.1 --port 8000
```

Default HTTP requests are refused. Put a trusted HTTPS proxy in front before real LAN use. Tests create an app explicitly in insecure loopback mode, never by default.

## API contract

| Endpoint | Authentication | Purpose |
|---|---|---|
| `POST /auth/bootstrap` | One-time bootstrap secret | Create first administrator and its first device |
| `POST /auth/login` | Device ID + issued device secret | Obtain 24-hour session |
| `GET /auth/me` | Bearer session | Current user/device |
| `POST /admin/users` | Admin session | Add a user |
| `POST /auth/pairing-invites` | Admin session | Make 5-minute single-use invite for user |
| `POST /auth/pair` | Invite token | Enroll device and issue credential/session |
| `GET /auth/devices` | Bearer session | List own devices |
| `POST /auth/devices/{id}/revoke` | Owner or admin session | Revoke credentials, sessions, pending invites |

`/auth/bootstrap` JSON example:

```json
{
  "username": "admin",
  "display_name": "Administrator",
  "name": "My Linux PC",
  "platform": "linux",
  "identity_public_key": "temporary-client-generated-public-key-or-random-device-string",
  "bootstrap_secret": "environment-secret-value"
}
```

The returned `device_secret` must be treated as a high-value credential. Never display it in logs or browser diagnostics. Use `Authorization: Bearer <access_token>` for protected endpoints.

## Validation

```bash
python -m pip install -r server/requirements-dev.txt
python -m unittest discover -s server/tests -v
```

Tests include one-time bootstrap, wrong secret, pairing one-time use/expiry, ownership checks, privileged endpoints, token expiry and device revocation. Do not mistake API tests for browser E2E tests; WebdriverIO begins after a UI exists.

## Migration

`connect()` upgrades existing SQLite v1 databases to v2 by applying `migrate_v2.sql`; back up a real database before migrating. Legacy devices from v1 do not have credentials and must be re-enrolled using a future managed migration workflow. As the project is pre-deployment this is an acceptable limitation.
